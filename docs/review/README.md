# 研究審查機制 / Research Review System

這個資料夾讓外部 agent（或人）對本專案做一次**完整、可重複、可跨次比對**的審查。

## 這是什麼

本專案的終點是**一篇可投稿的論文**（中途需能展示階段成果），判準從嚴。
審查要回答四件事：

1. **意圖 ↔ 實作是否一致** —「我宣稱要做的事」與「程式實際做的事」是否相符（**核心命題**）
2. **程式是否有 bug**
3. **有沒有可優化之處**
4. **方向是否正確** — 這些工作有沒有在往可投稿論文前進

## 資料夾結構

| 路徑 | 內容 |
|---|---|
| `context/` | **受審宣稱**：研究目標、資料、方法、評估、程式碼地圖、意圖對照表、已知弱點 |
| `protocol/` | **審查程序**：任務書 + 四個 block（D 資料 / C 程式碼 / M 方法與方向 / R 審查文件本身） |
| `reports/` | 每次審查的報告，一次一個資料夾 |
| `2026-09-10-research-review-system-design.md` | 這套機制本身的設計 spec |

## 審查者：從這裡開始

**閱讀順序（照順序，不要先亂逛 repo）：**

1. 本檔
2. `protocol/PROTOCOL.md` ← 完整規則、材料分級、執行紀律、報告格式都在這
3. `context/00-overview.md` → `06-open-issues.md`（依序）
4. `reports/` 中最新一份報告（若有）— 為了做 delta
5. 之後才依 `protocol/block-*.md` 去讀程式碼與 `dataset/`

**使用者希望你多討論。** 遇到需要他裁決的事（意圖無記載、多種解讀、優先順序取捨）
請主動提問，不要悶頭產出報告——規則見 `protocol/PROTOCOL.md` §0.6。
但能自己用指令查到的事實，一律先查。

**最重要的一條規則：** `context/` 與 `PROGRESS.md` 裡的每一句話都是**待驗證的宣稱**，
不是事實。唯一權威是程式碼與 `dataset/` 的實際內容。兩者不符就是 finding。

## 維護者：什麼時候要更新 context/

`context/` 在下列情況會過期，**每次 review 前需確認**：

- 現行 pipeline 的程式碼有改動（`05-traceability.md` 的 `file:line` 會漂移）
- `dataset/` 增減檔案或重新產生
- 研究目標、系統定位、成功判準有變動
- 跑出新的實驗結果（`03-evidence.md` 的證據台帳要更新）

與 `PROGRESS.md` 的分工：`PROGRESS.md` 是 append-only 開發流水帳，回答「做過什麼」；
`context/` 是靜態審查脈絡，回答「現況是什麼、為什麼這樣、程式在哪」。
